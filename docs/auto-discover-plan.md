# 自动发现 DNS 污染并加速：方案与实施记录

> 目标：减少「手动加域名」的人工操作。
> 本文记录三档方案的取舍、实测依据与当前进度。**档位 A 已实现**，B/C 仅作记录，未实施。

## 一、为什么不能一步做到全自动

核心限制不在代码，而在**判定信号的可靠性**：

1. **没有干净参照**。判 DNS 污染的理想做法是拿一个不受干扰的信道（海外 DoH / 代理）作基准。但这台机器长期在国内网络，`1.1.1.1`、`dns.google` 完全不可达（`server/probe.ts` 的注释已记录此事）。没有基准，就只能靠「多方不一致 + 连不通」推测。
2. **「源不一致」误报高**。实测国内两家 DoH（AliDNS / DNSPod）对 CDN 域名各自返回不同边缘节点，这是正常的多 IP 轮询。
3. **写错代价高**。自动写入 hosts 后客户端会直连该 IP。判错会导致变慢或区域性不可用，比不改更糟。

### 实测数据（2026-11-22）

| 域名 | 源不一致 | 系统≠DoH | TLS 成功 | 判定 |
|---|---|---|---|---|
| twitter.com | ✓ | ✓ | 0/4 | 真污染（且不可加速） |
| www.google.com | ✓ | — | 0/18 | 真污染（SNI/IP 封锁） |
| fonts.googleapis.com | **✓** | — | 2/2 | **误报** |
| cdn.jsdelivr.net | **✓** | — | 11/11 | **误报** |
| cdnjs.cloudflare.com | — | — | 4/4 | 正常 |
| fastly.jsdelivr.net | — | — | 8/8 | 正常 |
| registry.npmjs.org | — | — | 24/24 | 正常 |

结论：**「源不一致」不能单独作为污染证据**，CDN 类域名误报率约 2/5。

## 二、关于公共清单（gfwlist / china-list）

实测结论：**都不适合当候选源**。

| 清单 | 内容 | 对本项目的价值 |
|---|---|---|
| gfwlist | 被 GFW 屏蔽的域名 | **不适用**：多为 SNI 阻断或 IP 封锁，改 hosts 无效 |
| v2fly `geolocation-cn` | 国内有接入点的域名 | **不适用**：本来就直连良好，不需要加速 |
| v2fly `geolocation-!cn` | 国内无接入点的域名 | **部分适用**：需逐个探测筛选，命中率低 |

抽样实测（从 `geolocation-!cn` 取 3 个）：`ankiweb.net` 4/4、`scorecardresearch.com` 8/8、`uxthemes.com` 4/4 —— **全部本来就能通**，没有一个是需要加速的。

所以候选来源的正确选择是**抓包会话**：记录的是真实访问过的域名，最贴近实际需求瓶颈。

## 三、档位 A：只发现不自动写（✅ 已实现）

### 定位

把「发现哪些域名值得加速」自动化，但把「要不要写」留给人。

### 实现

```
抓包会话（data/capture/*.json）
  → extractHosts()：去重、排除 localhost/IP
  → 跳过已加速 / 已屏蔽 / 已判 SNI 阻断
  → 逐批探测（并发 5，单轮上限 40 个域名）
      ├─ measureSystem()：走系统 DNS 测完整耗时（dns+tcp+tls+ttfb）
      └─ probeDomain() + measureCandidate()：找候选最优，同样测完整耗时
  → judgeCandidate()：判定
  → data/discover/{sessionId}.json（只存建议，不写 hosts）
```

### 判定规则

```
1. 已在屏蔽清单          → handled（不参与）
2. 已在加速列表          → handled
3. SNI 阻断              → unusable（换 DNS 无效）
4. 没有 IP 能握手        → unusable（写了反而打不开）
5. 系统解析全部不通      → recommend
6. 候选比当前快 ≥80ms    → recommend（附收益毫秒）
7. 源不一致但系统可用    → noop（CDN 正常多节点，不固定单 IP）
8. 其余                  → noop
```

**80ms 阈值的作用**：同一 IP 连测两次差 30ms 很常见。为了几十毫秒改写 hosts 不划算，还会牺牲 CDN 的多节点调度能力。

### 踩过的坑：两侧量纲必须一致

第一版用 `probeDomain` 的 `candidate.latency` 当候选耗时，而那是**纯 TCP 握手**（10~50ms）；系统侧却是**完整耗时**（100~400ms）。两者相减，凭空多出几百毫秒的「收益」——baidu 的 9 个域名全被判成「快 380ms（97%）」。

修正后改为对候选 IP 也跑一次 `resolveAndMeasure`，同量纲对比：

**修正前**（9 个域名）
```
recommend: 8, noop: 1
gips2.baidu.com   sys=392  cand=12   → 快 380ms（97%）  ← 假的
```

**修正后**
```
recommend: 2, noop: 7
gips2.baidu.com            sys=312  cand=130  → 快 182ms（58%）  建议加速
psstatic.cdn.bcebos.com    sys=238  cand=113  → 快 125ms（53%）  建议加速
www.baidu.com              sys=175  cand=177  → CDN 多节点，不建议
```

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/local/discover/:sessionId` | 分析会话，产出建议（会真实探测，较慢） |
| GET | `/local/discover/:sessionId` | 读取上次结果，不重新探测 |

采纳**复用已有的** `/local/custom-add`，不新增写入路径——写入逻辑只有一处，行为可预期。

### 界面

抓包页新增「待确认加速」卡片：结论徽标、当前解析耗时 vs 候选最优、判定依据、勾选后「采纳选中」。

### 待观察

- 单轮 40 个域名的上限是否合适（大站点如电商、视频站可能上百个域名）
- 80ms 阈值是否需要按地区/ISP 调整
- 建议采纳后应观察实际效果，若变慢则说明判定偏乐观

## 四、档位 B：高置信度自动写（未实施）

### 前置条件（必须先有）

1. **自动撤销机制**。没有它，不建议开自动写。
   - 写入后 24 小时内持续监控该域名成功率
   - 成功率低于阈值（如 <80%）或耗时劣化 → 自动删除该条自定义域名
2. **刷新 `inconsistent` 的 CDN 误报**。当前判据对 CDN 误报 2/5，直接用于自动写会主动制造问题。

### 建议的准入条件

只有同时满足以下全部条件才自动写：

- `systemDiffers === true`（系统解析不在 DoH 候选集内，中等强度信号）
- 候选 IP 完整耗时比系统快 ≥ 150ms（比人工档更严）
- 连续 3 轮探测结论一致（排除单次抖动）
- 该域名属于「用户近期真实访问过」（来自抓包，不是公共清单）
- 不在任何白名单（如涉及登录/支付的域名，固定 IP 风险高）

### 风险

- 固定 CDN 单节点可能导致跨地域访问变慢
- 云服务商轮换 IP 后需及时更新，否则域名直接不可用
- 用户不知情时 hosts 被改动，排障困难

### 建议实现方式

- 默认关闭，需在设置里显式开启
- 每次自动写入都记录可审计日志（何时、依据、撤销条件）
- 提供「一键回滚全部自动写入」入口

## 五、档位 C：接入公共清单批量扫描（未实施）

### 可行部分

仅 `geolocation-!cn` 有参考价值，且**只做发现、不做自动写**。

### 主要障碍

| 问题 | 数据 |
|---|---|
| 清单规模 | `geolocation-cn` 2311 行（1704 条纯域名，其余为 include 引用） |
| 单域名耗时 | 1.4s ~ 4.5s（失败域名更久，`www.google.com` 18 个候选全失败要 30s+） |
| 3000 域名一轮 | 约 2~3 小时，需夜间跑并限速 |
| 预期命中率 | 低（抽样 3 个全部「本来就能通」） |

### 若要做

1. 只取 `geolocation-!cn` 中**纯域名条目**，展开 `include:` 引用
2. 分批限速（建议并发 ≤3，避免影响正常浏览）
3. 结果只进「待确认加速」列表，与档位 A 共用界面
4. 定期（如每周）重扫，观察清单变化

---

## 六、当前建议

**保持档位 A**，先积累真实判定样本：

1. 用一段时间，看「建议加速」的域名采纳后是否真的变快
2. 若发现建议偏乐观（采纳后变慢），说明 80ms 阈值偏低或测量噪声大，需调参
3. 收集足够的「建议正确/错误」样本后，再评估档位 B 的阈值能否定准

**在自动撤销机制做出来之前，不建议开档位 B。**
